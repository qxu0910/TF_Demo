# 自动提交并推送

在当前项目完成一次修改任务后执行同步。沿用用户在会话或项目规则中的持续授权，不重复确认；技能本身不构成其他仓库的推送授权。未明确授权的项目，先完成本地检查，再确认具体目标和待推送内容。

## 工作流程

1. 读取项目 `AGENTS.md`，检查仓库根目录、`git status --short --branch`、当前分支、远端 URL 与上游分支。目标必须与用户授权一致；不要从其他项目复制仓库地址，也不要擅自新建仓库或改写远端。
2. 检查本次任务差异，包括已暂存内容和新增文件。运行与修改相符的检查；若检查失败，先修复本次引入的问题，无法解决时说明阻碍，不把未完成修改作为已完成任务自动推送。
3. 只暂存本次任务相关文件或修改块，使用明确路径。保留用户原有的未提交和已暂存工作；不能可靠分离同一文件中的更改时先澄清。不要使用无差别的 `git add .` 或 `git add -A`，不要提交凭据、真实 `.env`、依赖或临时产物。
4. 复核暂存差异后，用描述实际修改的消息提交。无本次修改时不创建空提交。发现已有未推送提交时，确认它们也属于已授权范围后才推送。
5. 将当前分支推送至已核实的上游。没有上游时，为用户授权的远端设置同名分支上游，例如 `git push -u origin <当前分支>`。Detached HEAD 或目标不明确时先解决分支归属，不擅自推送到默认分支。
6. 检查推送退出码，确认远端目标分支的提交标识与本地一致，并检查最终工作区状态。报告提交短标识、目标仓库/分支及同步结果；保留的用户修改应如实说明。

## 失败处理

- 不使用强制推送、破坏性重置、绕过 hooks 或分支保护。远端领先、认证失败或保护规则阻止推送时保留本地提交，报告原因；不要无限重试或擅自合并、变基。
- 网络或沙箱权限导致失败时，按运行环境的审批机制请求必要权限；既有用户授权不能绕过环境权限。不要读取或输出令牌来规避登录。
- Windows 上，若经核实仓库由沙箱账号创建而授权进程由用户账号运行，可对该明确路径使用单次 `git -c safe.directory=<仓库绝对路径> ...`；不要全局设置 `safe.directory=*`。

此技能由代理在任务结束时执行，不安装文件监听器、Git hook 或定时任务。
